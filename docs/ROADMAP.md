项目处于 Windows 桌面壳与真实输入联调阶段。当前首要事项是定位 Phase 6 的音频发送积压；没有进入 AI 整理、语音编辑或外部 Beta 阶段。

本文只维护进度、阻塞和下一步。详细历史与命令保留在 [TESTING](TESTING.md)，设计见 [ARCHITECTURE](ARCHITECTURE.md)，产品范围见 [PRODUCT_SPEC](PRODUCT_SPEC.md)，取舍见 [DECISIONS](DECISIONS.md) 。本次文档校准依据已有代码和测试记录，不代表重新执行了语音测试或关闭了阻塞。

本次修订已完成本地一致性检查；Claude 外部复核未完成，原因见 TESTING。新增的后续设计尚不能视为已复核实施方案，不影响此前已授权的发送诊断范围。

## 主要阻塞

1. **持续慢发送根因未定。** 首轮相同 10 秒静音对照中，Python 两次本地发送阶段约 10 秒，C# 为 29.32／22.45 秒，最慢一次 send 达 11.54 秒；无需麦克风、WPF 或 TSF 就能复现。但两次 Python 和一次 C# 未在原五秒窗口内等到结束确认，不能据此认定 Python 网络正常。v2 将核对本地缓冲、连接差异及收尾阶段。此前真实语音日志已确认冷连接 ready 时积压 47 块、丢 2 块后触发 `AudioQueueOverflow`；连接前采集已局部修正，真实效果待验证。
2. **多段稳定性未验收。** 早期多段测试出现 `InvalidDataException`。后续三次诊断复测均只有一个 final，不能证明两段及以上已修复。
3. **启动与兼容性待验证。** 较早 2.47–3.25 秒启动等待与 30 秒预热过期相关；延长到 180 秒仍不能消除过期后的冷启动。中英混说、Chrome 真实语音和更广应用兼容没有完整验收。
4. **旧 native 激活测试仍失败。** legacy direct activation harness 的 `E_INVALIDARG` 与已通过的 31 项 live 检查分开报告，不以局部通过代替全套通过。

## 下一步：v2 缓冲与收尾对照

按 [TESTING 的 v2 对照步骤](TESTING.md#next-v2-cloud-run) 执行，不要求反复朗读来比较传输：

1. 保持旧 Desktop 托盘程序退出，在持有 Key 的 PowerShell 再运行同一条 `send_probe.py` 命令，确认显示 `Diagnostics v2`。仍使用相同 10 秒合成静音和四轮顺序；工具改用独立的 `send-probe-v2` 测试输出，正式 Desktop 不变。当前工具进程没有 Key，新版云端结果待用户执行。
2. 比较 Python 上下层发送缓冲、C# 连接/TLS 事件及代理解析、慢发送完成观测；区分结束指令发送失败、等待确认超时、较晚确认和断连。五秒检查点后最多观察到二十秒，仅针对诊断工具，不调整产品等待策略。不能将本地 send 返回或缓冲为零当成服务端收到，更不能以纯静音验证识别准确率。
3. 传输证据分析后，再使用已有 `tsf-ready-capture` Desktop，确认 `diagnostics=5 capture_policy=after_provider_ready`。先做预热后的 Notepad 短句，再单独验证超过 190 秒后的冷启动；冷连接显示 Connecting，看到 Speak now 才开始说话。要求没有连接期间积压，收到非空 partial 且无音频丢弃。该修复不消除冷连接等待，也不保证慢发送已解决。
4. 发送积压定位并处理后，再恢复至少两个 final segment、自然停顿、停止重启、键鼠接管和焦点变化验收；逐项记录 Notepad 与 Chrome 结果。HUD 错误提示自动隐藏不在本轮修改范围。

在这些证据出现前，Phase 6 保持进行中。不得自动重放不确定写入、切换目标补写，也不把长语音或 AI 功能加入当前排障。

## 后续顺序（尚未实施）

每项单独界定范围和验收，以下不是一次性开发授权：

| 顺序 | 目标 | 进入条件 |
| --- | --- | --- |
| 1 | 稳定连续输入、明确录音／错误反馈 | 完成当前发送积压和多段输入验证 |
| 2 | 最近稳定结果可主动复制；手动个人词典 | 主链路稳定后分别设计；确定内存上限、清除规则和供应商热词能力，不默认存音频 |
| 3 | 基础 Document Engine、目标同步、局部替换与 Undo | 已验证目标身份、选区／版本及人工修改冲突处理 |
| 4 | 默认 None、可选 Light；明确选区／简单替换语音编辑 | 第 3 项具备后；整理不得阻塞显示或覆盖人工修改 |
| 5 | 更复杂引用、保守的 Voice Send、按需应用适配 | 简单编辑可靠；发送意图和目标规则分别验收 |
| 6 | 小规模外部 Beta、安装分发及必要后端 | 核心体验通过；供应商密钥保护与数据边界先完成 |

微信输入法和 Typeless 的借鉴已合并到产品、架构和验证要求：实时反馈、失败可取回、专有词和受控整理。未选择竞品模型，也未引入自动文风、全文上下文、长期音频历史、云同步、完整 IME 或商业化系统。
